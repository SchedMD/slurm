Hierarchical Resource (HRES) Scheduling

Overview

Hierarchical Resources (HRES) were added in Slurm 25.05 in a Beta state. While in beta, the configuration file format and other aspects of this feature may undergo substantial changes in future versions and require major changes to avoid errors. Sites that utilize this feature while in a beta state should pay particularly close attention to changes noted in RELEASE_NOTES and the CHANGELOGs when upgrading.

Hierarchical Resources allow for license-like resources to be defined as part of independent hierarchical topologies and associated with specific nodes. Jobs may request any integer count of that resource. Multiple resources may be defined in the configuration (in a resources.yaml file), and will use independently defined hierarchies.

Although these hierarchical topologies have some similarities to network topologies, the definitions for each are completely separate.

Planning Modes

Three modes of resource planning are provided. In either case, a layer may be defined with a count of zero or infinite (count: -1) resources, with the impact of this depending on the mode used. Every layer is identified by a unique layer_name; nodes and count are optional, and count defaults to zero.

Mode 1

In Mode 1, sufficient resources are only required on one layer that overlaps with job allocation. In many cases only a single level is needed. However, multiple levels may be defined if some additional flexibility in where resources are used is preferred, as described in the example below.

A layer with a zero count of a resource will have no impact on scheduling. Since that layer will never satisfy the request, it will never alter the calculated list of nodes eligible to run a given job. It would be semantically equivalent to removing that layer definition.

A layer with an infinite count of a resource will the always allow a new job allocation to succeed. Unless prevented due to other requirements, jobs will be able to execute immediately.

For example, consider the natural resource defined in the example resources.yaml file below. A job that requests this resource and is allocated node[01-04] will pull from the pool of 100 available to node[01-16]. With a count of 50 specified at the higher level (node[01-32]), they can be allocated in addition to the resources specified in each group of 16. That is, 100 each would be available to each group of 16, and 50 more would be available on any of them, for a total of 250 of this resource.

Mode 2

In Mode 2, sufficient resources must be available on all layers on all levels that overlap with job allocation. Note that scheduling stalls are possible if higher levels do not make enough resources available.

A layer with a zero count of a resource will have a significant impact on scheduling. All nodes underneath that layer would never be able to satisfy the allocation constraints. This could be used to mark that resource unavailable for a specific portion of the cluster, e.g., for hardware maintenance, without altering the individual lower-layer resource counts.

A layer with an infinite count of a resource will have no impact on scheduling. Since that layer will always satisfy the request, it will never constrain execution and would be semantically equivalent to removing that layer definition.

For example, consider the flat resource defined in the example resources.yaml file below. A job that requests this resource and is allocated node[01-04] will pull from all levels that include those nodes. So it would pull from the 12 available on node[01-08], from the 16 available on node[01-16], and from the 24 available on node[01-32]. Since the highest level only contains 24, that is the maximum that can be allocated, even though a larger total is available on lower levels. This example allows a fixed set of resources to have some flexibility in where they are used.

Mode 3

In Mode 3, resources are allocated on a per-node basis, with the total consumption being calculated from the most granular layer and summed up into the successively higher layers. This mode is specifically designed for consumable resources like power, where the total usage at a higher level (e.g., cluster-wide) is the sum of the usage of its components (e.g., chassis level, then rack level summing multiple chassis, then datacenter row ).

The scheduler ensures that the total summed resources at every layer in the hierarchy do not exceed that layer's defined count.

Important Note: Layers defined under Mode 3 must be able to be represented as a rooted uniform depth tree. Every layer except the root names its parent with parent_name, and nodes may only be listed on leaf layers. Each parent inherits the union of its children's nodes.

For example, consider the power resource defined in the example resources.yaml file below. A job that requests 1000 of the power resource and is allocated node[01-16] will pull from all levels that include those nodes. So it would pull 8000 from node[01-08], 8000 from node[09-16], 16000 from node[01-16], and 16000 from node[01-32].

Preemption

A pending job can preempt lower-priority running jobs to reclaim a Mode 3 resource. Because per-node usage is summed into every layer above it, a job holding the resource under a shared layer is a preemption candidate even when it does not share any nodes with the preemptor. Preemption is governed by the usual PreemptType and PreemptMode configuration; only the CANCEL and REQUEUE preemption modes are supported for Mode 3 resources. Preemption to reclaim a hierarchical resource is not supported for Mode 1 or Mode 2 resources.

Plugins

An HRES plugin lets an external service take part in the life of the jobs that use a resource, for example to reserve the resource when a job starts, pass data to the job's nodes, release the resource when the job ends, and take a layer out of service when the service reports a problem. A plugin is enabled per resource with the plugin section of resources.yaml. Currently only hres/lua is available.

- resource: qpu
  mode: MODE_1
  plugin:
    type: hres/lua
    config:
      - name: path
        value: /etc/slurm/hres_qpu.lua
    maintenance_cycle: 60
    maintenance_timeout: 10
  layers:
    - layer_name: qpu1
      nodes:
        - "node[01-16]"
      count: 1

Callbacks

When a job uses several resources with a plugin, the callbacks run in the order the resources are defined in resources.yaml, and the epilogs run in the reverse order. The pre-runs stop at the first failure, every other callback of a kind runs even after one of them fails. A plugin may return ESLURM_HRES_REMOTE_FAIL to report that the external service is unavailable rather than broken.

The pre-run, revoke and controller epilog run while slurmctld holds its job lock, which stops scheduling and most requests until they return. They must be quick. Slow work belongs in the maintenance callback, or in the asynchronous pre-run of hres/lua.

CallbackRunsOn failure

This is before the usage of running jobs is restored, so every layer is shown with nothing used ESLURM_HRES_MAINTENANCE_DISABLE or ESLURM_HRES_MAINTENANCE_DOWN disable every layer of the resource, any other error is fatal

What the nodes receive about each resource is taken when the job starts: the resource name, the plugin configuration, the job's plugin arguments, the payload from the pre-run, and the layers the job holds, each with the amount charged and the job's nodes under it. It does not change while the job runs, even if the layers do. It travels in the credential of each job step, which srun receives, so the job's user can read the plugin configuration, the payload and the arguments. They must not hold secrets.

Plugin Arguments

A job may pass arguments to the plugin of a resource at the end of its request, after the count if one is given. The arguments are only handed to the plugin, Slurm does not interpret them:

sbatch --license='qpu:1[mode=fast,shots=1000]' my_script.sh

Each argument needs both a name and a value, without whitespace, and a name may be given only once. A resource takes one set of arguments. Arguments are not allowed for a license that is not a hierarchical resource. They are shown in the Licenses and LicensesAlloc of the job.

hres/lua

hres/lua runs a Lua script, given by the path entry of the plugin config. The script must be available at the same path on the controller and on the nodes, and be readable by every user running jobs with the resource, because hres_node_user_task_prolog loads it as the user. WARNING: Most of its functions run as root or as SlurmUser, so the script and every directory on its path must be writable only by root. It must define every function below except hres_controller_job_async_prerun, which is optional. Each function returns a Slurm return code, such as slurm.SUCCESS, slurm.ERROR or slurm.ESLURM_HRES_REMOTE_FAIL. A missing or non-numeric return value means success. If the script cannot be loaded, for example because a function is missing, the error is logged and the callback fails. slurmctld does not start if the script cannot be loaded, and later keeps using the last script it loaded, except for hres_controller_job_async_prerun, which fails.

hres_create_context(ctx, layers)
hres_destroy_context(ctx)
hres_maintenance(ctx, layers)
hres_controller_job_prerun(ctx, job, prep)       -- returns rc[, payload]
hres_controller_job_async_prerun(ctx, job, prep) -- optional, returns rc[, payload]
hres_controller_job_revoke(ctx, job, prep)
hres_controller_job_epilog(ctx, job, prep)
hres_node_job_prolog(prep, job)
hres_node_job_epilog(prep, job)
hres_node_task_prolog(prep, job, node_tid, global_tid)
hres_node_task_epilog(prep, job, node_tid, global_tid)
hres_node_user_task_prolog(prep, job, node_tid, global_tid)

The arguments are tables:

  • ctx: name of the resource and config, the plugin configuration as a name = value table
  • layers: an array of the resource's layers, each with name, nodes, total, used and disable_layer. hres_maintenance may set disable_layer on a layer to stop allocating from it, and clear it to enable the layer again
  • job: job_id, sluid, user_id and nodes
  • prep: what the nodes receive about the resource: name, config, plugin_args (a name = value table), payload and layers, an array of the layers the job holds, each with name, count and nodes

A string returned as the second value of hres_controller_job_prerun becomes the payload sent to the job's nodes, as prep.payload. When hres_controller_job_async_prerun is defined, it runs after the pre-run in a separate thread, while the job stays in the CONFIGURING state, and its payload, if any, replaces the one from the pre-run. If it fails, the job is requeued, or cancelled if it cannot be requeued. If the job's nodes are not allocated after all, its result is dropped and hres_controller_job_revoke is called. The job is not scheduled again until the asynchronous pre-run ends. As the revoke can run while the asynchronous pre-run of the same job is still running, the service must treat a revoke as final for that run of the job, identified by job.job_id and job.sluid, and refuse or undo a later reservation from it.

The controller functions of a resource share one Lua state, except hres_maintenance, which has a state of its own, and hres_controller_job_async_prerun, which gets a new one for each call. Globals set by the other functions are not visible to them. A state is reloaded when the script changes, which drops its globals without calling hres_create_context again. Each node function runs in a new Lua state. hres_node_task_prolog and hres_node_user_task_prolog run in the task's process, so the latter may write to the task's output, flushing it before returning. hres_node_task_epilog runs in slurmstepd after the task exits.

A node function that runs longer than PrologTimeout, or EpilogTimeout for the epilogs, fails with an error and is handled like any other failure of that function (see the table above). Both default to PrologEpilogTimeout, which is not set by default, so there is no limit. The limit only stops Lua code: a function blocked in a command or a read, as in os.execute() or io.popen(), is not interrupted, so bound such calls in the script, for example with timeout(1).

function hres_controller_job_prerun(ctx, job, prep)
	slurm.log_info("reserving %s for JobId=%d", prep.name, job.job_id)
	return slurm.SUCCESS, "token=" .. job.job_id
end

function hres_node_job_prolog(prep, job)
	slurm.log_info("JobId=%d payload %s", job.job_id, prep.payload or "")
	return slurm.SUCCESS
end

Limitations

  • This implementation is in a beta state (see overview)
  • Resource names defined through the hierarchical resources configuration must not conflict with any cluster licenses
  • The layer structure (layers, variables, and modes) is static. Changing it requires editing resources.yaml and restarting or reconfiguring (see Runtime Updates)
  • PreemptParameters=reclaim_licenses in slurm.conf applies only to regular licenses, not to HRES. Mode 3 resources are instead reclaimed by their own preemption path (see Preemption)
  • Preemption to reclaim a Mode 3 resource is only performed by the main scheduler, not during backfill scheduling
  • The licenses of a running job that holds or requests an HRES cannot be changed with scontrol update job. Requeue the job and change them while it is pending
  • A hierarchical resource cannot be requested with the | form of a license request

Runtime Updates

Administrators may change the nodes, count, base, and disabled state of an existing layer with scontrol update. A plain Nodes list replaces the layer's nodes, while a + or - prefix adds or removes nodes. Count is absolute and must not be lower than the layer's BaseUsage. Base replaces the whole base list, and an empty Base= clears it. In Mode 3, Nodes may only be changed on leaf layers. Node and base changes are propagated to the ancestors. Running jobs are never affected, so lowering a count below the current usage makes new jobs wait until usage drops.

A running job keeps the layers it was charged on, even when those layers later gain or lose nodes. The job releases exactly what it took, so changing the nodes of a layer under a running job does not distort the usage counts. The layers a job holds are shown by the LicensesAlloc field of scontrol show job, for example power(rack1*1000,row1*1000,datacenter*1000):1000, each layer followed by the amount charged on it. In Mode 3 that amount grows with the number of the job's nodes under the layer, as in rack1*2000 for two nodes.

scontrol update HRESName=power LayerName=rack2 Nodes=+node[33-36] Count=45000
scontrol update HRESName=power LayerName=rack1 Base=

The same operation is available through the REST API as POST /slurm/v0.0.46/hres/ with a JSON body containing hres_name, layer_name, and any of nodes, count, base, disable_hres, and disable_layer.

Changes to the nodes of a layer are saved in the slurmctld node state file (in StateSaveLocation), and are recovered as follows when slurmctld starts or is reconfigured:

  • Dynamic nodes and cloud nodes keep their saved layers after a restart or scontrol reconfigure.
  • Other nodes keep their saved layers only when slurmctld is started with -R or when a backup slurmctld takes control. A default restart or scontrol reconfigure returns them to the layers defined in resources.yaml. So when the primary slurmctld resumes control without -R, it returns these nodes to their configured layers, even though the backup kept their saved layers.
  • When a node is powered down, or fails to resume within ResumeTimeout, it returns to its configured layers: those in resources.yaml, or for a dynamic node, those it was created with. A node that is powered down or powering down when slurmctld starts also uses its configured layers.
  • When a node's saved layers are recovered, they replace its membership in every layer defined in resources.yaml. Edits to resources.yaml do not change that node's layers until it returns to its configured layers. If a saved layer no longer exists or is no longer a leaf layer, all of the node's saved changes are discarded and an error is logged.

Changes to the count, base, and disabled state are not saved. resources.yaml is read again on the next reconfigure or restart, and those changes are lost.

Disabling a Resource

A resource or a single layer may be switched off without removing it from the configuration. DisableHRES applies to every layer of the resource, whether or not a layer is named, while DisableLayer applies only to the named layer, so jobs may still be allocated resources from the other layers. Both accept only true and false. Jobs may still request a disabled resource, but they stay pending until it is enabled again. A job that no enabled layer can serve pends with the reason HRESDisabled. Running jobs keep the resources that they already hold. The same fields may be set in resources.yaml as disable_hres and disable_layer.

scontrol update HRESName=power DisableHRES=true
scontrol update HRESName=power LayerName=rack1 DisableLayer=true

Viewing a Resource

scontrol show license prints one entry per layer.

LicenseName=power
    Total=35000 Used=0 Free=35000 Reserved=0 Remote=no
    LayerName=rack1 ParentName=row1 Nodes=node[01-08] Mode=3 DisableHRES=false DisableLayer=false ConfTotal=40000 BaseUsage=5000
    Base=storage:5000
  • LayerName, ParentName: the layer and, when it has one, its parent layer
  • Mode: the planning mode of the resource
  • DisableHRES, DisableLayer: whether the resource or the layer is disabled for scheduling
  • ConfTotal: the count configured for the layer
  • BaseUsage: the sum of the base values of the layer, plus, in Mode 3, the base usage propagated up from its children
  • Base: the base name and value pairs, or (null)
  • Total: what is left for jobs, the configured count minus the base usage

Dynamic Nodes

Dynamic nodes are not listed in resources.yaml. They name their layers when they are created, through the HRES= node parameter, which is a JSON list of resource name and layer name pairs. In Mode 3 only one leaf layer per resource may be given.

scontrol create NodeName=node33 State=cloud HRES='[{"hres_name":"power","layer_name":"rack2"}]'
slurmd -Z --conf 'HRES=[{"hres_name":"power","layer_name":"rack2"}]'

The node is added to the listed layers and their parents when it is created, and removed from all layers when it is deleted. An unknown or unsuitable layer creates the node without HRES membership and logs an error. The parameter is ignored for nodes defined in slurm.conf. Layers given at creation are the node's configured layers. Runtime changes to them are kept across restarts until the node is powered down, as described in Runtime Updates.
